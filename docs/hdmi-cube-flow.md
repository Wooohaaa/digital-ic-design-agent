# 多 Codex HDMI 旋转立方体工程试验

目标板为 HX1P35A / PH1P35MDG324，时钟50MHz，依据用户提供的 HDL2604 手册及原理图确定直连 HDMI 差分引脚。工程位于 `benchmarks/hdmi_cube/`。采用 640×480、25MHz 像素时钟、125MHz DDR 串行时钟（约59.52Hz），输出兼容 HDMI 显示器的 DVI/TMDS 视频；不包含音频或 HDCP。

## 实际分工

IC Forge 持久任务 `7269aae60e5a` 的主管和外部 Codex 执行者均显式指定 `gpt-6-luna`，并发上限6。六个独立进程分别负责时序、TMDS、三维几何、双缓冲绘制、安路 PHY 和补充 testbench；根据各任务的开始/完成时间戳计算，最高实际并发为6。随后执行顶层/约束集成及只读审查。原生会话、每次执行的日志、补丁和隔离工作树保留在 `.fpga-agent/tasks/7269aae60e5a/`（本地运行记录，不随仓库提交）。

立方体围绕 Y/X 两个轴进行固定点三维旋转，逐顶点投影，再用 Bresenham 绘制12条边。两个 640×480 一位片上帧缓冲交替清空/绘制，只在垂直消隐交换已完成缓冲。后台必须在420000个像素周期以内完成一帧，不依赖外部 DDR 或预存图像。

## 独立验收

宿主 `fpga_agent.video` 持有检查器，模型执行者不能编辑 `verification/` 或检查器源码。检查包括：

- 两个完整800×525光栅及消隐/同步边界。
- 全字节、连续差异和确定性随机 TMDS 序列，独立解码及实际传输位差异校验。
- 全部256个角度的8顶点，与独立整数规格及高精度旋转误差界限比较。
- 双缓冲启动、提前交换拒绝、绘制时限、越界读、复位恢复和三幅完整 RTL 帧；全部12条边与独立 Bresenham 参考比较。
- 三通道序列化的位序、字边界、差分极性和转发时钟。
- 从顶层差分端口恢复完整 TMDS/RGB/同步视频流，与独立模块捕获的帧逐像素对照，检查所有流水线对齐。
- 原生 TD 综合、布局布线、ERAM 映射、精确引脚电气标准及 setup/hold 时序门禁。

仿真报告与当前 HDL、规格、testbench、检查器哈希绑定。启动重验即使旧报告失效；重验失败留下失败报告。宿主验收调用 TD 时不改写输入 manifest 的状态字段，避免无意义的输入指纹变化触发整轮重跑。交付包同时收录并校验显式声明的规格和验证入口。

```powershell
python benchmarks/hdmi_cube/verification/acceptance.py
icforge verify benchmarks/hdmi_cube
icforge package benchmarks/hdmi_cube
```

## 本轮暴露的 agent 问题

1. 主管显式选模型时忽略原生 Codex 配置，导致认证通道与执行者不一致；已改为保留 provider 并显式传模型。
2. 批次集成树与名为 integration 的子任务目录冲突；已采用 workers/ 命名空间，并恢复本轮独立工作树，保留六个完成节点。
3. 分波等待会让就绪任务空等慢任务；已改为依赖就绪持续补位，并记录调度事件。
4. Windows 批处理补丁套壳可陷入 UTF-8/命令行长度/结束标记错误循环；已加入明确平台建议与有界自动恢复。
5. 暂停消耗了尝试次数；已分离真实失败、启动次数和工具恢复次数。
6. 长 JSON 事件可能被普通终端长行切片损坏；原生事件使用独立的有界预算。
7. 等待节点可能看不到批次期间新要求；现在派发前消费并持久保存补充要求。

实际运行结果、实现状态和硬件显示验收分别记录，不能把仿真帧当作实板照片，也不能把一次工程试验等同于对任意复杂任务或无限时运行的保证。实板结果见下文；本轮使用终端 FFmpeg 和 JTAG 命令完成采集与下载。

## 实际验收结果（2026-11-05 更新）

最终主工程使用 25 MHz 像素时钟和 125 MHz DDR 串行时钟；独立 RTL 验收与原生 TD full 均通过。setup WNS +5.746 ns、hold WNS +0.066 ns、TNS 均为 0，STA 覆盖率 99.99%；847 LUT6、38 ERAM、4 DSP。当前合格位流 SHA-256 为 `8a91ebb24042e39ec3d17c9442c25864391914f8ec6232cd021def545b698431`。

两次独立 SRAM 重载后，分别进行了 14 秒和 20 秒连续 Hagibis 采集。舍弃前 5 秒接收端锁定期，18/18 与 30/30 个采样帧全部匹配独立几何参考，且姿态持续变化。实板 GIF 在 README 展示，原始 MKV、PNG 和哈希报告进入交付包。没有写入 Flash。详细机器证据见 `hdmi-cube-hardware.json` 与工程 `reports/hardware-video.json`。

## 本轮硬件调试与 agent 改进

- 最初单独约束 TMDS N 端并驱动 B17/HPD，偏离了用户提供的安路示例。最终只输出 TMDS33 P 端，由 TD 配对 N 端，B17 留作未驱动输入侧信号；使用原厂外部反馈 PLL/ODDR 拓扑。
- LED1/LED2/LED3 的含义只适用于明确驱动这些引脚的诊断位流。完整立方体诊断版证实 PLL 锁定和像素时钟运行；不能从未驱动的 LED 状态推断 PLL。
- 仅取 1–2 秒采集会错过约 3 秒的接收端重新锁定，开头还可能是残留帧或损坏 MJPEG。新命令默认采集 12 秒、丢弃前 5 秒，再比较多个姿态。一个好帧、彩条或静止图不能通过旋转验收。
- 原 ODDR 占位检查把 d0/d1 的边沿写反。宿主按 UG1310 修正为 d0 上升沿、d1 下降沿并保持成对输入；增加 16 个时钟相位和输入位间延迟案例，明确这只是可综合分支的功能仿真，并非原厂时序仿真。
- 对照发现：原纯黑背景版本失锁，完整立方体叠加彩条与 RGB(1,1,1) 版本能出图。关闭未用 DRP/phase 时钟虽匹配原厂接法，但单独修改未解决失锁；半周期串行器输入暂存实验也未解决，因此未保留该推测性改动。
- **显式兼容设置**：最终背景为 RGB(1,1,1)，视觉近黑，并在规格与独立 RGB 验收中准确记录。仍保留严格黑色参数 `BACKGROUND_LEVEL=0`；该模式在当前链路未通过，具体电气/接收端原因未确定。这是有证据的兼容方案，不是掩盖纯黑失败或宣称普适根因修复。
- 下载器每次生成独立 SVF 文件，把实际扫描载荷逐字节绑定到合格 `.bit` 二进制主体。文件头时间戳改变可能不改变扫描载荷，不能仅凭两个整文件哈希不同就断定旧文件复用。SVF 的 IDCODE 检查与成功执行不等于配置回读或功能验收。
- 新增跨进程、随进程退出自动释放的板卡独占锁，覆盖下载与采集。并行 agent 不得在别人测量时重新配置开发板。测试进程与真实板级操作也必须隔离资源。
- `icforge video-hardware` 可经 CLI/TUI 调用；自然语言模型选择的动作只采集现有合格下载，显式 `--program` 才请求 SRAM 下载。`icforge flow --hardware-video` 串接仿真、TD、下载、采集与打包。
- 工程声明 `hardware_acceptance.required=true` 后，工程审查、打包和长期任务完成检查都要求当前实板证据；失败重跑立即撤销当前成功状态。修改 RTL、位流、检查器或证据文件后，相关门禁会过期。

上述操作方法同时保存在 agent 内置 `hx1p35a-delivery` 技能的 HDMI 参考中，长期任务可通过技能加载与历史检查点继续执行。
