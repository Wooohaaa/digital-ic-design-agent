# IC Forge 技术白皮书

### 面向数字 IC / FPGA 工程的终端 Agent —— 从需求到可复现证据链的完整闭环

> 竞赛展示版 · 2026-11-26
>
> 本文聚焦三件事：**它做出了什么**、**它坚持什么理念**、**它用什么技术实现**。
> 所有数字均来自仓库内已保存的报告与实测记录。

---

## 0. 一句话定位

IC Forge 不是一个"帮你写 Verilog 的聊天机器人"。

它是一个**持有独立验收权的工程 Agent**：生成设计，却把尺子交给验证侧；
每一个结论都附带指纹绑定、可重放、可审计的证据；
整套系统把 LLM 的创造力，约束进了一条**可证明、可回退、可交付**的工程流水线。

同时，它是一个**多 Agent 编排器**：把有明确边界的工作派发给本机 Codex、Claude Code、
OpenCode，在隔离 worktree 中并行执行，由宿主工程门禁统一验收。

规模：13,407 行 Python（`fpga_agent/`），38 个测试文件、217 个测试函数，
CI 矩阵 Python 3.11 / 3.12 × Windows / Linux 全绿。

## 1. 先进理念：五条定义下一代工程 Agent 的原则

这些不是口号，而是直接写进代码结构、退出码与门禁逻辑的硬约束。

### 1.1 设计者与验证者分离

> Agent 生成设计，验证方持有独立规格、参考模型、测试与门禁。

这是整个系统最核心的架构决策。在 `docs/flow.md` 中明确规定：

- 普通 RTL 模块：模型只写 `rtl/`、`tb/`、`spec/design.md`，**验证目标从需求导出并冻结在 `project.json`**
- CPU：模型**只生成 RTL**；独立 Python ISA 参考、受保护 testbench、退休/存储/内存/SoC 签名全部由验证侧固定
- 自动修复循环最多 5 轮，且**冻结已接受的 testbench 与验收目标**——修复只能改 RTL，不能改尺子

这一条从根上消除了 LLM 参与工程时最典型的失效模式：**为了让测试通过而悄悄改测试**。

### 1.2 证据链优先于声明

每个候选版本都保留完整链条：

```
需求 → 实现 → 仿真/形式证据 → 综合/物理证据 → 指标 → 接受或回退
```

形式化后为：

- 输入与配置绑定 SHA-256，复制到独立 `build/lec/<run-id>/inputs/`
- 报告记录状态、命令、工具版本、证明点与产物指纹
- `lec_valid()` 重验输入、checker、产物与证明清单
- 任一环节变化 → 依赖它的上层证据自动失效

"一次生成成功、自测 PASS、增加代码量" 在路线图中被明确排除在"进化"之外。

### 1.3 工程状态是一道精确的状态机

LEC 的返回码被严格区分：`0 = pass`、`2 = 工具缺失 blocked`、`1 = 失败 / 超时 / 需进一步证明 / 输入错误`。
每一类状态在门禁中都有确定语义并映射到不同处理路径。

交付层把 `artifact_ready` 与 `engineering_signoff` 设计为两个独立字段：
前者描述"证据已就绪到位流与报告"，后者承载更高层级的工程授权。
**分层授权让每一层结论都精确标注作用域，避免越权表述。**

### 1.4 冻结契约下的可量化进化

`docs/rsi-roadmap.md` 定义：只有在**独立验收和固定预算下得到可重复改进**，才计作进化。

每轮实验固定 workload、验证器版本、模型版本/输入、搜索预算和工具环境；
保留基线与候选、失败原因、质量/性能/资源变化及人工干预次数；
**留出从未用于候选修复的评估集**；
改动验证器则单独审阅并重建证据，不沿用旧分数。

这套方法把"AI 有没有进步"从主观印象变成了可复算的实验科学。

### 1.5 人机协同的清晰契约

人提供方向、现实资源边界、签核、PDK、设备与物理操作；Agent 在明确授权的范围内自主推进。
例如 TD 流程由本机工程门禁负责，实板编程由用户执行，工艺/封装/DFT 进入专门阶段规划。

**职责边界清晰，是长期自动化可信的前提，也是系统设计成熟的标志。**

## 2. 系统架构与关键技术

### 2.1 分层结构

```
┌─────────────────────────────────────────────────────────────┐
│  交互层    Textual TUI · CLI (icforge) · 受限工具集           │
├─────────────────────────────────────────────────────────────┤
│  认知层    Planner · 上下文预算/压缩 · 技能发现 · 历史回忆     │
│            (context_budget.py / knowledge.py / task_planner.py)│
├─────────────────────────────────────────────────────────────┤
│  编排层    持久任务 · 后台 worker · worktree 隔离 · 多 Agent   │
│            (autonomy.py / orchestration.py / agent_backends.py)│
├─────────────────────────────────────────────────────────────┤
│  工程层    需求/设计 · 仿真 · lint · LEC/形式证明 · CPU 验证   │
│            (project.py / riscv.py / lec.py / spec_proof.py /  │
│             cpu_external.py / cpu_act.py / cpu_stage2.py /   │
│             cpu_rv64.py / sv39_accept.py)                    │
├─────────────────────────────────────────────────────────────┤
│  实现层    Anlogic TD 适配 · 位流/交付打包 · 硬件证据          │
│            (td.py / programmer.py / hardware_evidence.py)    │
├─────────────────────────────────────────────────────────────┤
│  门禁层    工程审查 · artifact readiness · 分层签核            │
│            (quality.py / spec_gate.py / evidence.py)         │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 关键技术一：三层形式等价验证体系

`fpga_agent/lec.py` + `lec_state.py` + `lec_reset.py` 构成三层证明，覆盖从组合到时序的完整谱系：

| 方法 | 证明内容 | 适用对象 |
|---|---|---|
| `direct` | `equiv_make` → `equiv_simple -undef` → `equiv_status -assert`；要求每个 `$equiv` 的 A/B 合并、有可观察输出、证明点非空 | 组合逻辑 |
| `state-bijection` | 完整状态双射 + 初态集合 + 异步复位事件 + 全部下一状态/输出义务的 SAT 证明 | 状态保持型时序设计 |
| `reset-state-relation` | 显式复位后状态关系，支持状态合并（schema 3） | 复位后收敛的多周期设计 |

工程取舍体现成熟度：**不使用弱时序归纳、不开启忽略未知单元或环境假设**。
golden 与 synthesis 共享 Yosys 前端，配合独立语义差分形成互补验证；
`-undef` 按确定模型处理并明确记录在证据契约中。

配置 `"formal_equivalence": {"required": true}` 后，LEC 成为真正的门禁：
直接影响 artifact readiness、长期任务完成判断与交付打包，
并随 TD 公共入口在仿真门禁后复用有效证明。

### 2.3 关键技术二：独立 ISA 参考 + 差分 + 官方签名

CPU 验证由四层独立机制叠加：

1. **独立 Python ISA 参考模型**：不复用 RTL，逐指令比对 PC、指令、目的寄存器与写入值
2. **Unicorn 外部参考差分**：比对每次退休、每笔 store、最终 RAM
3. **RISC-V ACT 官方架构测试**：固定 `riscv-arch-test@96e3589a`，编译原始源码，逐签名字比对
4. **EEI 契约冻结**：RV32I 2.1 终止型 EEI、RV64I 2.1 小端单 hart，终止条件写入契约

**变异测试**被纳入流程：检查器必须能找到注入的错误，否则不算有效验证。
这让验证系统本身可被证伪，而不是一套只会输出 PASS 的橡皮图章。

### 2.4 关键技术三：证据指纹与失效传播

`fpga_agent/evidence.py` 实现基于 SHA-256 的证据绑定：

- 输入、配置、checker、脚本、产物全部指纹化
- 任一环节变化 → 依赖它的上层证据失效
- 交付 ZIP 携带原始报告、网表、脚本、快照、日志，打包前后复核字节指纹
- 从 ZIP 解包后可重新执行门禁（"交付还原"测试覆盖此路径）

这解决了 AI 生成工程中最隐蔽的问题：**证据与代码悄悄脱节**。
在这里，证据不是一次性附件，而是随代码共同演化的活体。

### 2.5 关键技术四：跨 Agent 编排与固定宿主验收

`orchestration.py` 的设计要点：

- 主管模型**只读规划**；执行者仅在自己的 worktree 内获得实现权限
- 支持本机 Codex / Claude Code / OpenCode，各自使用原生账号与配置
- 主管凭据**不自动传给执行者**，需显式 `ICFORGE_EXECUTOR_` 前缀覆盖
- 通用任务要求预先声明 `.icforge/checks.json`；**主管不能在任务中替换验收配置**
- 有 `tests/` 时默认运行 Python unittest，其它工程显式提供检查

**Agent 可以分工，但验收权始终在宿主**——这是多 Agent 系统可信协作的基石。

### 2.6 关键技术五：有界上下文与可迁移流程知识

借鉴 OpenCode / Hermes / Command Code 公开机制后独立实现：

- 默认 96,000 字符输入预算，预留 8,000 字符空间，分阶段裁剪可重读数据
- 保护用户目标、追加要求与已加载技能；核心内容超预算时明确阻塞并支持恢复
- 裁剪内容保存至 `context-full.json`，每步日志独立留存，历史可分页找回
- 技能目录兼容 `.icforge` / `.agents` / `.opencode` / `.claude` / `.commandcode` / `.hermes`
- 同名技能不静默覆盖；外部技能附带脚本不会自动执行
- `recall` 结果带来源与 `historical_only` 标记，历史成功与当前验收严格区分

### 3.4 Stage 3 RV64 工程基线

- RV64I 2.1：**30 条整型计算指令**，六种条件分支、JAL/JALR、七种 load、四种 store、FENCE
- 机器态运行时：`mtvec` / `mepc` / `mcause` / `mtval` / `mscratch` 与 MIE/MPIE，六种 CSR 形式与 MRET
- 独立 **Sv39 三级页表遍历器**：规范地址、4 KiB/大页、SUM/MXR、Svade A/D、非法 PTE 与访问错误
- 裸机 LLVM 编译 C checksum 通过 LP64 调用约定启动
- 物理基线：ECP5 LFE5U-85F CABGA381、20 MHz、固定种子 7 的 out-of-context nextpnr 路由

### 3.5 实板证据

- **HDMI 旋转立方体**：两次独立 SRAM 重载，采集卡分别接受 **18/18** 与 **30/30** 个视频样本，均识别多个旋转姿态；setup/hold WNS **+5.746 / +0.066 ns**，TNS = 0
- **TinyStories260K**：模型完整性 CRC、logits 与生成 token 完成板上验收

## 4. 演进路线：从 EDA Agent 到全计算体系

项目以**七阶段验收路线图**定义长期目标，每阶段都有明确产物与进入下一阶段的证据条件：

| 阶段 | 目标 | 当前进展 |
|---|---|---|
| 1 Agent-driven EDA | SV 前端、仿真、UVM 最小契约、综合、严格 LEC、统一 Agent API | 组合/时序/复位三层 LEC 已闭合；SV/UVM 有界契约 v0.14 含 29 用例、38 特性 |
| 2 RV32I CPU | 自主生成 CPU、独立参考、架构测试、时序 LEC | 三种微架构通过独立比对与 ACT 2.7.4；Stage 2 终止型 EEI 已冻结 |
| 3 RVA23 商用 CPU | 64 位应用处理器、存储体系、SoC、软件栈 | RV64I 30 指令、机器态陷阱、独立 Sv39 遍历器、ECP5 物理基线已建立 |
| 4 tiny GPU | PTX 子集、SIMT 执行与存储模型 | 退出条件已定义 |
| 5 推理 LPU | 编译器、runtime、权重/激活/KV 数据流 | 退出条件已定义 |
| 6 数据中心训练与推理 | 可扩展训练 GPU、推理 LPU、互连与编排 | 退出条件已定义 |
| 7 全计算体系重构 | CPU/SoC + GPU/LPU 联合探索 | 退出条件已定义 |

路线图设计了**局部交叉试验机制**：现有 RV32I 直接作为 Stage 1 的回归负载，无需等待所有 SV 功能完成。
这体现了务实的工程推进智慧——**用可验证的局部成果驱动长期目标，而非线性等待**。

## 6. 总结

IC Forge 的技术价值不在"生成 RTL 的能力"，而在**把 LLM 的创造力约束进可验证、可回退、可审计的工程闭环**：

1. **独立性** —— 设计者与验证者分离，尺子不由被考核者持有
2. **可证伪性** —— 每个结论绑定输入指纹与可重放证据，证据随代码共同演化
3. **严谨性** —— 状态机化的工程语义，让每一层结论精确标注作用域
4. **可迁移性** —— 流程知识与多 Agent 编排跨工具链复用，验收权始终在宿主
5. **长期性** —— 以冻结预算和留出评估集衡量进化，而非一次生成的高光

这是一套面向 AI 时代硬件工程的**治理架构**，
把"能写代码的模型"升级为"能对工程结果负责的 Agent"。
